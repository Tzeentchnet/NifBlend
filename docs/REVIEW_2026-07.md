# NifBlend Review — July 2026

> Point-in-time audit of the addon for correctness, security, and completeness
> issues. Findings are severity-ordered; each links the affected file(s) and
> the fix that lands (or landed) for it. See [`CHANGELOG.md`](CHANGELOG.md)
> for the per-fix changelog entries as they ship.

## Methodology

Review focused on the per-game bridge layer (`nifblend/bridge/`) and the
operators that wire it into Blender (`nifblend/ops/`), cross-checked against
the test suite (`nifblend/tests/`) and the project roadmap
([`ROADMAP.md`](ROADMAP.md), [`newroadmap.md`](newroadmap.md)) to distinguish
intentional out-of-scope gaps from unintentional wiring bugs.

## Findings

### 1. [CRITICAL] Imported/exported shapes ignore their own transform

`NIFBLEND_OT_import_nif.execute()` ([`nifblend/ops/import_nif.py`](../nifblend/ops/import_nif.py))
never set `obj.location` / `.rotation_euler` / `.scale` / `.matrix_world` from
the source block's `translation` / `rotation` / `scale` fields (inherited from
`NiAVObject`). [`mesh_data_to_blender`](../nifblend/bridge/mesh_in.py) only
built mesh geometry, never object placement. The mirror bug existed on
export: [`mesh_data_to_bstrishape`](../nifblend/bridge/mesh_out.py) hardcoded
`blk.translation = Vector3(0, 0, 0)`, an identity `Matrix33` rotation, and
`blk.scale = 1.0` unconditionally. Any multi-part NIF, or any shape sitting
under a non-identity parent `NiNode`, imported and exported with every piece
stacked at the world origin.

**Status:** fixed — see Phase 4 / Phase 5 changelog entries.

### 2. [CRITICAL] Materials, skin weights, and armature never wired into import or export

The pure bridge layer (`material_in.py` / `material_out.py`,
`armature_in.py` / `armature_out.py`, `skin_in.py`) is complete and
unit-tested, but no operator called most of it:

- **Import:** [`ops/import_nif.py`](../nifblend/ops/import_nif.py)'s per-block
  loop called only `import_bstrishape` / `nitrishape_to_mesh_data` /
  `nitristrips_to_mesh_data` + `mesh_data_to_blender`. `NiNode` blocks fell
  into the `skipped` bucket entirely — no armature was ever built. Only the
  Starfield `BSGeometry` branch (`_import_bsgeometry`) called
  `material_data_to_blender` + `apply_skin_to_object`. Dangling (zero
  operator callers): `import_material`
  ([`material_in.py`](../nifblend/bridge/material_in.py)), `import_armature` /
  `ninode_tree_to_armature_data` / `armature_data_to_blender`
  ([`armature_in.py`](../nifblend/bridge/armature_in.py)),
  `niskin_to_skin_data` / `bstrishape_skin_to_skin_data`
  ([`skin_in.py`](../nifblend/bridge/skin_in.py)).
- **Export:** [`ops/export_nif.py`](../nifblend/ops/export_nif.py) and
  [`ops/export_batch.py`](../nifblend/ops/export_batch.py) called only
  `export_bstrishape` → `mesh_data_to_bstrishape`, which hardcoded `skin=-1`,
  `shader_property=-1`, `alpha_property=-1`. None of
  [`material_out.py`](../nifblend/bridge/material_out.py)'s `export_material`
  family or `armature_out.py`'s skin builders were ever called.
- **Gaps in the bridge layer itself:**
  [`armature_out.py`](../nifblend/bridge/armature_out.py) had no
  bone-hierarchy/`NiNode`-tree builder (only skin-partition builders
  existed), and no function anywhere harvested a `SkinData` from Blender
  vertex groups (only the NIF→`SkinData` decode direction existed).
- **Root cause:** the pure bridge functions are thoroughly unit-tested, but
  operator-level integration tests lagged — confirmed by the prior absence of
  `test_import_nif_op.py` / `test_export_nif_op.py` (unlike `import_kf`,
  `import_cell`, `skyrim_conversion`, which do have operator-level tests).
  This is how ~600 green tests coexisted with this gap: every phase's pure
  decoder/builder shipped with full coverage, but the "wire it into the
  actual operator" step was only completed for the Starfield import slice.

**Status:** fixed — import wired in [`nifblend/ops/import_nif.py`](../nifblend/ops/import_nif.py);
export wired in [`nifblend/ops/export_nif.py`](../nifblend/ops/export_nif.py)'s
new `build_export_table` (reused by
[`export_batch.py`](../nifblend/ops/export_batch.py) per-object), with two
new pure functions added to close the bridge-layer gaps:
[`build_ninode_tree`](../nifblend/bridge/armature_out.py) (bone hierarchy,
inverse of `ninode_tree_to_armature_data`) and
[`skin_data_from_vertex_groups`](../nifblend/bridge/skin_in.py) (harvest
`SkinData` from Blender vertex groups, inverse of `apply_skin_to_object`).
Export scope is deliberately bounded to `BSTriShape` (no classic `NiTriShape`
geometry builder exists yet) and skips `NiSkinPartition` (a GPU-skinning
hint the import side doesn't consume for `BSTriShape` — see
`nifblend/bridge/skin_in.py`'s module docstring); both are called out as
follow-on items in the CHANGELOG entry. Note for future maintainers:
dispatching classic-vs-modern material resolution by checking whether
`.shader_property` / `.alpha_property` merely look like valid refs
(non-negative, not the null sentinel) is unsafe — these fields are
declared on every `NiGeometry`-family dataclass regardless of NIF version
(the codegen emits every version-gated field on one class), but are only
ever *populated* by the read path when `bs_version > 34`. On older files
they silently sit at the Python dataclass default of `0`, which is
indistinguishable by value from a genuine ref to block 0. Dispatch must
key on `isinstance(shape, BSTriShape)` instead (see
[`_resolve_shape_material`](../nifblend/ops/import_nif.py)).

### 3. [HIGH] Phase 10f/10g KF export was dead code

`NIFBLEND_OT_export_kf` ([`nifblend/ops/export_kf.py`](../nifblend/ops/export_kf.py))
was fully implemented but absent from `_CLASSES` and `_menu_func_export` in
[`nifblend/__init__.py`](../nifblend/__init__.py) (no File → Export menu
entry), had no `test_export_kf_op.py`, no sidebar button, and
[`newroadmap.md`](newroadmap.md) / [`CHANGELOG.md`](CHANGELOG.md) had no
10f/10g entries despite the operator code existing.

**Status:** fixed — registered, menu + sidebar entry added, test suite added.

### 4. [HIGH / SECURITY] Path traversal (CWE-22) in asset path resolution

`resolve_texture_path` / `_resolve_case_insensitive` / `normalize_nif_relative`
([`nifblend/bridge/textures.py`](../nifblend/bridge/textures.py)) never
stripped or rejected `..` segments and never verified the resolved path
stayed under the configured Data root. This affected texture relinking,
Starfield external mesh/material resolution via `PrefsExternalAssetResolver`
([`nifblend/bridge/external_assets.py`](../nifblend/bridge/external_assets.py)),
and the `mesh_root / rel` join in
[`nifblend/ops/import_cell.py`](../nifblend/ops/import_cell.py). A crafted
NIF / `.mat` / cell-CSV file could resolve and load files from outside the
configured Data root — practical risk: local file disclosure if the
resulting path is later packed into a `.blend` (Blender's "Pack External
Data") or otherwise shared.

**Status:** fixed — containment check added; traversal segments are rejected
before resolution is attempted.

### 5. [MEDIUM] Skyrim LE↔SE shader-flag converter was a silent no-op

`_LE_TO_SE_BIT_MOVES = ()` in
[`nifblend/bridge/games/skyrim.py`](../nifblend/bridge/games/skyrim.py) — the
sidebar "Convert LE→SE" / "Convert SE→LE" buttons only restamped
`bs_version`; no flag bits actually moved, which could mislead users into
thinking a real conversion happened.

**Status:** documented — UI now discloses that flag layout is currently
identical between LE and SE for every flag the codegen emits today, and only
`bs_version` is restamped. Populate `_LE_TO_SE_BIT_MOVES` if/when a real
discrepancy is found against vanilla files.

### 6. [INFO] CI/mypy documentation — initially looked like drift, actually already resolved

The Phase 1.1 `### Added` entry in [`CHANGELOG.md`](CHANGELOG.md) still
describes the original `mypy.ini` + `mypy --strict` CI gate, which reads as
stale against today's [`.github/workflows/ci.yml`](../.github/workflows/ci.yml)
(`ruff` + `pytest` only) if that entry is read in isolation. Further down
the same file, a `### Removed` entry already documents the deliberate
decision: the codegen-emitted `nifblend/format/generated/` layer isn't
strict-mypy-clean by design, so the gate had gone red and unused and was
removed along with `mypy.ini` / the `mypy` dev dependency. Not a silent
regression — just a two-entries-apart continuity gap a future reader could
miss.

**Status:** no action needed; downgraded from the original "drift" framing
after finding the existing `### Removed` entry during this pass.

### 7. [LOW] Unbounded allocation from malformed NIF counts

`_read_array` in [`nifblend/format/primitives.py`](../nifblend/format/primitives.py)
didn't sanity-check `count` against the remaining stream size before reading
— a corrupt or malicious NIF could trigger a large allocation attempt
(desktop-tool DoS; low severity since this isn't a network service).

**Status:** fixed — bounds check added, raises a clean `EOFError` instead of
attempting an oversized read.

### 8. [LOW] O(n²) greedy stripification

`triangles_to_strips` / `_find_next` in
[`nifblend/bridge/games/oblivion.py`](../nifblend/bridge/games/oblivion.py)
rescans the full triangle list per step. Fine for typical Oblivion-era
meshes; could be slow on very high-poly ones. Already self-documented as
non-optimal in the module docstring.

**Status:** deferred — no action taken; revisit if profiling on a real
high-poly mesh shows it matters.

### 9. [HIGH] Half-precision `BSTriShape` vertex positions don't survive a byte round-trip

Discovered while adding operator-level test coverage for Phase 4's import
orchestration. `BSVertexDataSSE.read()` / `BSVertexData.read()`
([`nifblend/format/generated/structs.py`](../nifblend/format/generated/structs.py))
unconditionally construct the per-vertex `.vertex` field via
`Vector3.read()` (full-precision, 3×f32 = 12 bytes), regardless of the
`BSVertexDesc`'s full-precision flag (`0x400`). The fast vectorised path
([`vertex_dtype_for_desc`](../nifblend/format/primitives.py)) correctly
branches between `<f4` and `<f2` per-vertex position storage, but the
slow per-record path that `BSTriShape.read()` / `.write()` actually calls
does not. Since [`mesh_data_to_bstrishape`](../nifblend/bridge/mesh_out.py)
defaults to `full_precision=False` (half-float positions — the normal,
documented, performance-motivated default described in the README), the
writer emits 6 bytes/vertex for `.vertex` while the reader expects 12,
corrupting every subsequent field's byte alignment (reproduced in
isolation with a single-block table; not related to multi-block context).
The *only* reason the existing full binary round-trip test
([`test_bstrishape_full_binary_round_trip`](../nifblend/tests/test_mesh_out.py))
passes is that it explicitly opts into `full_precision=True`, sidestepping
the bug entirely.

**Impact:** every default-mode (half-precision) `BSTriShape` write → read
round-trip is broken today. This is likely the most severe correctness
bug found in this review, since half-precision is the default and the
documented performance win.

**Status:** documented, not fixed — the fix belongs in the codegen output
(`nifblend/format/generated/structs.py` is emitted, not hand-edited; see
[`tools/codegen/`](../tools/codegen/)), which is a separate body of work
from this pass's import/export orchestration wiring. Needs a fix in
`tools/codegen/emit.py`'s per-record compound emitter so the `#T#`-style
precision branch it already handles for the vectorised path is also
threaded through the individual `BSVertexData(SSE).read()`/`.write()`
methods, followed by `python -m tools.codegen` regeneration.

## Out of scope (unchanged)

Collision (`bhk*`), Havok constraints, morph/shape-key controllers
(`NiGeomMorpherController`), NLA-blend semantics beyond first-active-strip,
particle controllers, `NiControllerManager` synthesis, EGM/TRI files,
Starfield export. Tracked in [`ROADMAP.md`](ROADMAP.md).
